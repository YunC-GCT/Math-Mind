一、当前结论

现在公式 UI 观感差，不是数据库问题，也不是 KnowledgeModel 单点问题，而是渲染层仍停在“识别出公式块后用 ArkUI Text 显示 LaTeX 字符串”。所以 \frac、\sqrt、\sum 这些命令不会真正排版，短公式还会被拆成独立块，阅读体验接近 0。

不改数据库不把 HTML 入库先修原生链路最终统一 RichMath

二、当前程序真实状态

笔记详情页

NoteDetailBody
  -> NoteSectionView
     -> MarkdownRenderer
        -> MathTextRenderer
           -> splitMathText()

远端已并入 Markdown 编辑/渲染。笔记详情现在不是直接渲染纯文本，而是先走 MarkdownRenderer，再把段落或公式块交给 MathTextRenderer。

AI 对话窗口

ChatBubble
  -> MathTextRenderer
     -> splitMathText()

聊天气泡还没有经过 MarkdownRenderer，直接用 MathTextRenderer。这里是后续要统一的第二个入口。

数据来源

KnowledgeModel.contentFromFields()
  -> KnowledgeUnit.content / summary
  -> NoteDao.toBucket()
  -> knowledge_unit TEXT

数据库存的是纯文本和 Markdown/LaTeX 字符串。这个边界应保持不变，渲染结果不写回数据库。

已存在问题

MathTextParser.ets 里行内 $...$ 解析会把短公式拆成独立 formula block；公式 block 仍用 Text(block.content)。另外该段新代码有 C 风格 for，不符合 ArkTS strict 规则，实施时必须先改。

最终判断

应该采用“统一 RichMath 渲染层”，但落地顺序不能直接推翻现有 MarkdownRenderer。当前程序已经有笔记编辑与 Markdown 解析，因此最稳妥的路线是：保留 Markdown 作为外层块解析，新增 RichMath 作为数学内容内核。

这样可以同时解决笔记详情和 AI 对话：笔记继续保留 Markdown 标题/列表/代码块；聊天得到同一套公式混排和 fallback。

四、推荐架构

输入ChatMsg.content 或 KnowledgeUnit.content/summary，仍是纯文本。
Markdown 外层笔记详情继续使用 MarkdownParser 拆标题、列表、代码、公式围栏。
NormalizeLatexTextNormalizer 修复 /frac、全角符号、坏 delimiter。
Rich ParseRichMathParser 输出 paragraph、inline math、display formula、derivation。
RenderRichMathRenderer 优先 Web/KaTeX，失败走 native fallback。
接入MarkdownRenderer 和 ChatBubble 都调用同一数学内核。

关键设计原则

原则结论原因
数据库继续保存纯文本/Markdown/LaTeX保证编辑、检索、AI 再结构化不被 HTML/SVG 污染。
笔记详情保留 MarkdownRenderer 外壳远端已新增编辑器和 Markdown 渲染，不能绕开这套能力。
聊天气泡直接接 RichMathRenderer聊天没有 Markdown 外层，内容短，适合直接富文本渲染。
真公式排版正式版使用 Web/KaTeXArkUI Text 无法真正 typeset \frac、矩阵、aligned、根号。
失败兜底任何公式渲染失败都显示原始文本不能出现空白或详情页崩溃。

五、文件级方案

5.1 新增文件

文件职责关键接口/说明
entry/src/main/ets/shared/math/RichMathTypes.ets 统一类型 RichBlock、RichToken、FormulaMode、RenderSource、RenderIssue。类型显式，禁止 any/unknown。
entry/src/main/ets/shared/math/LatexTextNormalizer.ets 文本清洗 normalizeMathText(text, source)。修复 /frac、\fract、\sqt、全角符号、OCR 替换符；返回 issues 便于日志。
entry/src/main/ets/shared/math/RichMathParser.ets 混排解析 parseRichMath(text): RichBlock[]。短公式留在 paragraph tokens，长公式为 displayFormula，连续公式行为 derivation。
entry/src/main/ets/shared/math/RichMathHtmlBuilder.ets 生成安全 HTML 生成完整 HTML 字符串，注入本地 KaTeX 和暗色主题。所有普通文本必须 escape，LaTeX 用 JSON 字符串注入。
entry/src/main/ets/shared/math/RichMathCache.ets 缓存 按 hash(text + source + themeVersion) 缓存 HTML，避免聊天列表重复构造。上限 80-120 条。
entry/src/main/ets/shared/components/RichMathRenderer.ets 正式渲染组件 输入纯文本，内部 normalize -> parse -> html -> Web；提供 source、compact、maxHeight、selectable。
entry/src/main/ets/shared/components/RichMathFallback.ets 降级渲染 不用 Web 时显示原始 LaTeX 文本块，保留横向滚动和较好的公式块视觉。
entry/src/main/resources/rawfile/katex/... 本地 KaTeX 资源 最小化放置 katex.min.css、katex.min.js、字体。不要依赖网络。

5.2 修改文件

文件改动边界
entry/src/main/ets/utils/MathTextParser.ets 先修 C 风格 for；后续保留兼容导出，内部可委托 RichMathParser。 不要破坏 splitMathText(text): TextBlock[]，避免旧调用点断。
entry/src/main/ets/shared/components/MathTextRenderer.ets 退为 fallback 或 wrapper，主路线交给 RichMathRenderer。 不要立即删除，作为 Web/KaTeX 失败时的可读兜底。
entry/src/main/ets/shared/components/MarkdownRenderer.ets 保留 Markdown 解析能力；把 paragraph/formula block 中的数学内容交给 RichMathRenderer。 标题、列表、引用、代码块仍用原生 ArkUI；代码块不做数学渲染。
entry/src/main/ets/overlays/NoteDetailOverlay/NoteSection.ets 原则上继续调用 MarkdownRenderer，只在 MarkdownRenderer 内替换数学渲染内核。 不在 NoteSection 层重复判断公式。
entry/src/main/ets/overlays/AgentFloatWindow/chat/ChatBubble.ets 把用户/AI 两处 MathTextRenderer 换成 RichMathRenderer。 保留 Copy/Retry/Flag，不改 AgentChatService 调度。
agents/src/main/ets/agents/KnowledgeModel.ets 已有 prompt 约束：短公式 $...$，展示公式 $$...$$。后续只补“多行推导保持换行”。 不动分类职责、不动数据库结构。
entry/src/main/ets/services/AgentChatService.ets 仅追加回答格式提示：数学回答保留 LaTeX delimiter，不输出 HTML。 不在 service 层渲染，不把 HTML 发给模型。

六、分阶段落地

Stage 0

止血: 修当前原生链路

不引入 Web，不改页面结构，先让现有显示不再明显错误。

修正 MathTextParser.ets 的 C 风格 for；增加 LatexTextNormalizer；把 $x \to 0$ 这类短公式保留为行内 token，不再拆成独立大块。

验收短公式不再独占一行；/frac 可修成 \frac；原生 fallback 至少可读。
截断如果 Web/KaTeX 暂缓，Stage 0 也能显著改善观感。
Stage 1

RichMath 类型、清洗、解析

先建立统一数学语义层，不急着接业务页面。

paragraph(tokens: text | inlineMath)
displayFormula(latex, raw)
derivation(rows: displayFormula[])
验收5 类笔记样例都能解析出稳定块；连续等式合并为 derivation。
截断解析层是纯函数，可单独调试，不影响 UI。
Stage 2

HTML Builder + 本地 KaTeX

实现真正公式排版，但先离线验证 HTML。

生成一段完整 HTML，一条聊天消息或一个笔记分区对应一个 Web 上下文。不要每个小公式一个 Web，否则滚动和性能都会变差。

验收\frac{a}{b} 是上下分式；aligned 和多行推导能显示；长公式横向滚动。
截断如果 ArkUI Web 调试卡住，HTML 仍可在浏览器中验证。
Stage 3

RichMathRenderer 组件

封装 Web 加载、缓存、高度、fallback。

第一版不要追求复杂 JS bridge。可以先用估算高度 + 最大高度 + 内部滚动；Web 渲染失败时切到 RichMathFallback。

验收空内容不占高度；渲染失败不白屏；复杂公式不撑破父容器。
截断组件可先挂在独立测试页或临时样例页。
Stage 4

先接 AI 对话

聊天内容短，反馈快，适合先验证自然混排。

修改 ChatBubble.ets 两处调用。AI 气泡启用完整 RichMath，用户气泡可以先 compact 模式；复制仍复制原始文本。

验收20 条含公式消息滚动不卡；短公式和文字自然同行；Copy 结果仍是原始 LaTeX。
截断若性能不稳，先只给 AI 气泡启用 Web，用户气泡走 fallback。
Stage 5

再接笔记详情

笔记较长，应在 MarkdownRenderer 的 block 层接入，不做整页 Web。

NoteSection.ets 继续只调用 MarkdownRenderer。在 MarkdownRenderer 内：heading/list/quote/code 仍原生渲染，paragraph/formula 才进入 RichMath。

验收概念、定理、公式、证明题、计算题详情都能自然展示公式；编辑器保存后的 Markdown 仍能显示。
截断某个 section 渲染失败只 fallback 该 section，不影响整页详情。
Stage 6

回归与收尾

稳定后再考虑废弃旧主路线。

检查 rg "MathTextRenderer|splitMathText"。如果只剩 fallback 或无业务引用，再考虑降级旧组件职责。不要急着删除，保留回退点。

验收DevEco Studio GUI 编译；真机检查聊天、笔记详情、编辑保存、长公式滚动。
截断Web 不稳定时保留 Stage 0 原生改善版上线。

七、风险与处理

风险影响处理
ArkUI Web API 版本差异编译或运行失败第一版使用最小 Web 能力；失败走 fallback；不要依赖 API 11+ 特性。
Web 太多导致滚动卡顿聊天列表和详情页性能差一条消息/一个 section 一个 renderer；加 HTML 缓存；限制 maxHeight。
Markdown 与数学解析重复公式被错误拆块或代码块被渲染Markdown 做外层，RichMath 只处理 paragraph/formula；code 永远不进公式渲染。
AI 输出格式不稳定解析失败、显示原文Normalizer 兜底；KnowledgeModel 和 AgentChatService 只加格式提示，不改业务流程。
资源体积增加包体变大KaTeX 资源最小化；确认 rawfile 打包；不引入网络 CDN。
数据库污染编辑/检索/AI 再结构化变复杂严禁把 HTML、SVG、图片、KaTeX 输出写回 knowledge_unit。

八、最终验收标准

视觉验收

短公式自然嵌入中文段落；展示公式有稳定留白、暗色背景和横向滚动；多行推导合并成一个推导组；分式、根号、求和、积分不再显示为纯 LaTeX 字符串。

工程验收

不改 DB schema；不改 NoteDao；不改 Dispatcher；不改 TypeClassifier/KnowledgeModel 分类职责；DevEco GUI 编译通过；渲染失败有日志且页面不白屏。
