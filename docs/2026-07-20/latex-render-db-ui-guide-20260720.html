一、结论

数据库里存的是字符串，不是渲染结果

真实笔记写入 `MindTrace.db` 的 `knowledge_unit` 表。`content`、`summary`、`source` 都是 TEXT 字段；`tags`、`prerequisites`、`related`、`embedding` 是 JSON 字符串。也就是说，数据库负责保存原始/结构化文本，UI 负责解析和渲染。

RDBknowledge_unit.content普通 LaTeX 文本

当前 ArkUI 还不是真公式排版

项目已有 `MathTextParser.ets` 和 `MathTextRenderer.ets`，可以把文本拆成正文块和公式块，但目前公式块仍用 `Text(block.content)` 显示，所以 `\frac` 这类命令不会变成上下分式，只是被当作字符串展示。

当前可分块未真正 TeX typeset分式不会自动上下结构

二、当前真实数据流

1. OCR/输入TypeClassifier 提取文本，图片会调用 OCR，文本输入直接预处理。
2. KnowledgeModelAI 返回中文五类和 fields，公式要求保留为普通 LaTeX 文本。
3. 拼 content`contentFromFields()` 把字段拼成 `## 标题 + value`，再追加原文段。
4. 入库`NoteDao.insert()` 写入 `knowledge_unit.content` 和 `summary`。
5. 查询`NotesViewModel` / `HomeViewModel` 用 `NoteDao.queryAll/queryById` 拉取。
6. UI 渲染`NoteDetailBody -> NoteSectionView -> MathTextRenderer` 展示正文与公式块。

核心表字段

字段用途LaTeX 相关说明
content TEXT详情页主体内容最重要。保存 `## 摘要`、`## 条件`、`## 推导` 等分区文本，公式混在字段 value 内。
summary TEXT列表摘要和详情摘要可包含短公式，但列表页建议只做纯文本预览，避免复杂公式挤压。
tags TEXTJSON 字符串数组用于五类、学科、关键词，不承载公式。
source TEXT来源/原始材料说明当前可显示为“来源”，不建议继续展示大段 OCR 原文。

三、推荐的正式渲染链路

建议把“解析”和“排版”拆开，数据库仍保存纯文本，UI 在展示前生成渲染块。这样不会污染数据库，也方便后续替换公式渲染引擎。

从 RDB 只取 `KnowledgeUnit`

入口保持现有 `NoteDao.queryById()` / `queryAll()`。不要把渲染后的 HTML、SVG 或图片写回 `knowledge_unit.content`，否则后续编辑、检索和 AI 再结构化都会变复杂。

新增 `LatexTextNormalizer`

在进入解析前统一修正 OCR/AI 常见问题：`/frac` 转 `\frac`、全角符号转半角、连续空格清理、中文段落保留、成对补全 `$$...$$` 或 `\[...\]`。

升级 `MathTextParser` 为混排解析

不要只输出 text/formula 两种大块。推荐输出 paragraph/displayFormula/derivation 三层结构，paragraph 内再拆 inline text/math tokens。短公式留在句子里，长公式和多行推导才独立成块。

新增公式渲染组件

短期可继续用 ArkUI `Text` 显示规范化 LaTeX；要实现上下分式、根号、矩阵、aligned，对 ArkUI 原生 `Text` 不应抱幻想，需要引入真正的 TeX typesetting 路线。

推荐用 `Web` + 本地 KaTeX 作为公式组件

行内公式和展示公式都交给同一套 KaTeX 渲染能力，但使用不同容器：inline math 嵌在段落里，display math 才使用独立卡片和横向滚动。失败时 fallback 到原始 LaTeX 文本。

详情页只组合渲染块

`NoteDetailBody` 只负责分区和布局；`NoteSectionView` 调 `MathTextRenderer`；`MathTextRenderer` 决定段落、行内公式、展示公式和推导组如何组合。

混排判定规则

内容形态识别方式UI 呈现
行内短公式 `$...$`、`\(...\)`，或长度较短且不含 `\begin` / 多个等号 嵌在段落 Text/WebSpan 中，如“当 $x \to 0$ 时”。
展示公式 `$$...$$`、`\[...\]`、裸 `\frac`、`\sum`、`\int`，或长度超过 28 字符 独立公式块，左右留白、横向滚动。
多行推导 连续 2 行以上公式，或 `aligned/split/cases/matrix` 环境 推导组，行间距更紧，左侧轻提示线，不给每行套独立卡片。
解释文字 普通中文、英文说明、步骤描述 正常段落，行高舒适，公式 token 自然插入。

表达式

若函数 f 在点 a 附近有 n + 1 阶导数，则可以写成：

f(x)=f(a)+f'(a)(x-a)+...+ f(n)(a)n! (x-a)n+Rn(x)

其中 Rn(x) 是余项；如果只关心局部等价，可以使用 Peano 余项。

推导

Lagrange 余项适合在需要误差估计时使用：

Rn(x)=f(n+1)(ξ)(n+1)!(x-a)n+1 ξ 在 a 与 x 之间
|Rn(x)| ≤ M(n+1)!|x-a|n+1 若 |f(n+1)| ≤ M

这样文字解释、短公式和推导块在同一节里连续出现，不会被过多卡片打断。

注意

短公式应尽量行内显示，只有长公式、分式主体、多行推导才独立成块。渲染失败时显示原始 LaTeX 文本，不能让页面空白。

六、关键实现建议

1. 数据库不要改成 HTML

`knowledge_unit.content` 继续保存可编辑、可检索、可再结构化的纯文本。LaTeX 渲染是 view 层行为，不应把 Web HTML、KaTeX 输出或 SVG 反写入数据库。

2. 不要只靠正则一次性替换

应分两步：先 normalizer 做低风险修复，再 parser 分块。渲染组件只消费已经分好的公式块，不再猜测整段文字。

3. 原文段不建议默认展示

之前详情页暴露“原文”会放大 OCR 乱码和 `/frac` 问题。更好的做法是保留数据库原文用于追溯，但 UI 默认展示 AI fields 拼出的结构化内容。

4. 短公式不应强制成块

像 `$x \to 0$`、`$R_n(x)$`、`$a_n$` 这类短公式应该在段落中自然出现。只有长公式、分式主体、多行推导才使用独立容器。

5. 展示公式必须横向滚动

手机端复杂公式不能强行压缩。展示公式容器应固定宽度、允许横向滚动，正文仍正常换行。

6. 多行推导要合组

连续公式行应合成 derivation 组，用统一背景和紧凑行距承载，避免每一步都变成大卡片，导致阅读节奏被打断。

七、实施路线

阶段 A: 原生安全分块

先补 `LatexTextNormalizer`，升级 `MathTextParser`，让所有 `content/summary` 里的公式稳定进入 inline/display/derivation 三种形态。此阶段可先显示 LaTeX 文本，但排版层级必须正确。

阶段 B: Web/KaTeX 混排渲染

新增 `LatexFormulaView`、`MixedParagraphView` 和 `LatexDerivationView`，支持行内公式、展示公式、上下分式、上下标、根号、求和、积分、aligned。失败 fallback 到原始 LaTeX。

阶段 C: 详情页接入

只改 `NoteSectionView/MathTextRenderer`，不动 `NoteDao`、不动数据库表结构、不动 OCR、不动分类 agent。列表页仍使用纯文本摘要。

阶段 D: 验收与回归

用 5 类笔记各准备 2 条样例，覆盖正文、公式、证明步骤、计算过程。DevEco GUI 编译，真机检查滚动、字体、暗色背景和空白 fallback。

八、验收标准

  • 从 `NoteDao.queryById()` 拉出的 `KnowledgeUnit.content` 可以直接进入渲染链路，不需要预先改库。
  • 正文和公式分块稳定：`$$...$$`、`\[...\]`、`\(...\)`、裸 `\frac` 均能识别。
  • 短公式能自然嵌入正文，不被强制拆成独立卡片。
  • 连续多行推导能合并为一个推导组，不出现每行一个大框的割裂布局。
  • `\frac{a}{b}` 在正式渲染路径中呈现为上下分式，而不是显示 `/frac` 或 `\frac` 原文。
  • 复杂公式超出屏幕宽度时横向滚动，不撑破详情页布局。
  • KaTeX/Web 渲染失败时显示原始 LaTeX 文本块，并有错误日志，不出现空白。
  • 列表页不渲染复杂公式，只显示清洗后的纯文本预览，避免性能和布局风险。
  • 不修改 OCR、TypeClassifier、KnowledgeModel 分类职责；最多强化 KnowledgeModel prompt 的公式输出格式。
  • 不把 HTML、SVG、图片等渲染产物写回 `knowledge_unit.content`。

九、统一渲染架构: 同时覆盖 AI 对话和笔记详情

AI 对话窗口和笔记详情页现在已经都经过 `MathTextRenderer`：`ChatBubble.ets` 渲染消息内容，`NoteSection.ets` 渲染笔记分区内容。因此不要做两套公式渲染。建议新增一个统一的 `RichMathRenderer`，让两个入口共享 normalizer、parser、HTML builder、fallback 和缓存策略。

输入 AAI 对话消息：`ChatMsg.content`，来自 `AgentChatService.addAiMessage()`。
输入 B笔记详情：`KnowledgeUnit.content/summary`，来自 `NoteDao.queryById()`。
清洗`LatexTextNormalizer` 统一修复 `/frac`、乱码符、围栏和 delimiter。
分块`RichMathParser` 输出 paragraph/displayFormula/derivation。
渲染`RichMathRenderer` 优先 Web + KaTeX，失败走 native fallback。
呈现`ChatBubble` 和 `NoteSectionView` 只换渲染组件，不改业务逻辑。

为什么不是继续在 ArkUI Text 里拼

ArkUI `Text` 可以显示字符串，但不能把 `\frac{a}{b}` 真正排成上下分式，也很难在同一段落里同时处理中文换行、行内公式、展示公式和多行推导。为了自然混排，建议把一条消息或一个笔记分区作为完整 rich content 渲染，而不是每个公式单独塞一个 Web 小块。

一条消息一个 RichMathRenderer一个笔记分区一个 RichMathRenderer列表页不启用 Web 公式
