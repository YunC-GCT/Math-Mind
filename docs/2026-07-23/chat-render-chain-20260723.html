3. 三层根因 & 修复对应

🔴 Layer 1 — maxHeight 硬截断

MathTextRenderer.clampHeight 调用 Math.min(this.maxHeight, height)， @Prop maxHeight = 1800，且 ChatBubble / MarkdownRenderer 传 maxHeight: 4000。 内容超过 4000vp 全部裁切。

🔴 Layer 2 — render.html 溢出裁剪 + 高度测量死循环

html, body { overflow: hidden } + #content { overflow: hidden } 导致文档被 WebView 高度裁剪。getBoundingClientRect().height 返回裁剪后高度， WebView 永远无法扩展到真实内容高度 → 死循环。

位置修复

render.html:27-31移除 #content { overflow: hidden } 计划外
render.html:226-228measuredHeight 改为 Math.max(scrollHeight, getBoundingClientRect, 1) 双保险 计划外

🔴 Layer 3 — runJavaScript bridge 返回值超限

renderForCache 返回 "height\n" + encodeURIComponent(innerHTML)。 长内容 + KaTeX 渲染后 innerHTML 膨胀到 80–250KB → runJavaScript bridge 上限 ~64–256KB (因设备而异) → promise reject → webFailed = true → 退化到纯文本 (LaTeX/Markdown 全丢)。

6. 剩余风险

🟡 measureHeight 在首帧可能返回 0

render.html 首次加载时，scrollHeight 和 getBoundingClientRect().height 在 DOM 未完成布局时可能同时返回 0。双保险 (Math.max(..., 1)) 确保至少返回 1， 配合 clampHeight(minHeight=42) 确保 WebView 最低 42vp。但 42vp 对长内容来说几乎不可见， 直到 JS 回调更新高度。如果 JS 回调因任何原因未执行，用户将看到一条极细的气泡。

🟡 阈值 2800/5 需真机调优

当前阈值保守估计。某些高端设备的 ArkWeb bridge 上限可能更高 (256KB+)， 可以适当放宽让更多内容享受缓存加速。另：5 个公式的阈值是 display 公式 ($$...$$ / \[...\])，行内公式 ($...$) 不计入。

🟡 applyCachedRender 也可能超 bridge 输入限制

如果某个低于阈值的消息被缓存后，其 encodedHtml 因 KaTeX 膨胀变得很大， 后续 applyCachedRender 通过 JSON.stringify(cached.encodedHtml) 传给 bridge 时 作为输入参数 也可能超限。当前通过 MATH_RENDER_CACHE_MAX_CHARS=600000 阻止超大条目进入缓存，但此限制是对编码后大小而非原始 markdown，可能不够精确。

🟡 LazyForEach cachedCount=1 导致组件频繁销毁重建

AgentMessageList.ets:83 默认 cachedCount=1， 滚动出视口的 MathTextRenderer 被销毁。滚回时重新创建 WebView → 加载 render.html → 重新执行 runJavaScript。对长内容，每次重建都是 bridge 压力点。 建议将 cachedCount 提高到 3–5。
