数学富文本渲染重建方案

这版方案默认推翻旧的“先拆 text/formula，再用 ArkUI Text 显示 LaTeX 字符串”的路线，重新搭建一套统一的 Rich Math Renderer。目标是让 AI 对话窗口和笔记详情页都能自然显示“中文说明 + 行内公式 + 展示公式 + 多行推导”。

一、这版为什么会展示更好

旧路线的问题

公式像代码文本被打断分式不能上下结构

旧路线把公式识别成 formula block 后，仍然用 ArkUI `Text(block.content)` 显示。结果是 `\frac`、`\sum`、`\int` 等命令只是字符串，短公式也容易被拆成独立框，阅读节奏不自然。

文字: 当 $x \to 0$ 时
公式块: \frac{\sin x}{x}=1
文字: 所以可以替换

新路线的提升

自然混排真公式排版双入口统一

新路线把一段内容解析成 paragraph、display formula、derivation。短公式留在句子里，长公式才单独展示，多行推导合成一个推导组。AI 气泡和笔记详情共用同一套规则。

段落: 当 [inline: x \to 0] 时，[inline: sin x / x] 的极限为 1。
展示公式: \frac{\sin x}{x}=1
推导组: line1 -> line2 -> conclusion

二、最终视觉目标

AI 对话窗口

解释一下为什么当 x → 0 时可以用等价无穷小。

核心是短公式应该和解释放在一起：当 x → 0 时，sin x ∼ x，所以比值趋近于 1。

limx→0 sin xx = 1

这里展示公式只承担“重点结论”的作用，不把每个小符号都拆出去。

那泰勒展开怎么推？

可以把 sin x 在 0 点展开：

sin x = x - x33! + o(x3)展开
sin xx = 1 - x23! + o(x2)同除 x

连续推导放在一个组里，比每一行套一个框更自然。

展示会更好吗？

会更好，原因不是“加了公式库”这么简单，而是渲染单位变了：旧方案以公式为单位，新方案以语义块为单位。

AI 对话中，用户需要连续阅读解释，所以短公式必须跟文字粘在一起。笔记详情中，用户需要复习结构，所以长公式和推导要被突出，但不能每行都像卡片一样割裂。

这版方案同时满足两种场景：聊天更像自然回答，笔记更像整理好的讲义。

三、新架构

输入`ChatMsg.content` 或 `KnowledgeUnit.content`，都保持纯文本。
Normalize修复 `/frac`、乱码符、全角符号、错误 delimiter。
Parse拆成 paragraph、displayFormula、derivation。
HTML生成一段完整富文本 HTML，统一注入 KaTeX。
Render`RichMathRenderer` 用 Web 呈现，失败 fallback。
接入`ChatBubble` 与 `NoteSection` 都只调用同一个组件。

五、明确变更矩阵

实施时不要一上来删除旧文件。先新增新链路，再把两个调用点切过去，最后确认没有引用后再废弃旧链路。这样可以避免一半页面换新、一半页面仍依赖旧导出时编译失败。

5.1 新增文件

新增文件必须内容容易冲突的地方避让方式
entry/src/main/ets/shared/math/RichMathTypes.ets 只放类型：`RichBlock`、`RichToken`、`FormulaMode`、`RenderSource`、`RenderTheme`。 ArkTS 禁 `any/unknown`；联合类型过复杂时容易推断失败。 所有对象字段显式类型；不要写 `Record`；枚举值用字符串联合。
entry/src/main/ets/shared/math/LatexTextNormalizer.ets 纯函数：`normalizeMathText(text, source)`；修 `/frac`、全角符号、乱码替换符、delimiter。 可能误改普通路径 `/frac` 或 URL；可能把用户原文改坏。 只在检测到 `{...}{...}` 或数学信号时修 `/frac`；返回 `issues`，保留 `raw`。
entry/src/main/ets/shared/math/RichMathParser.ets 纯函数：`parseRichMath(normalized): RichBlock[]`；实现行内、展示、推导三类。 现有 `MathTextParser.ets` 仍被旧组件 import，直接替换会影响编译。 新建 parser，不覆盖旧 parser；旧 parser 后续做兼容 wrapper。
entry/src/main/ets/shared/math/RichMathHtmlBuilder.ets 把 RichBlock 生成完整 HTML，包含暗色 CSS、KaTeX 调用、错误 fallback DOM。 HTML 转义不足会把 AI 回复中的标签当 HTML；中文字符串写入容易乱码。 所有 text token 走 `escapeHtml()`；LaTeX 走 JSON 字符串注入；文件用 `apply_patch` 写 UTF-8。
entry/src/main/ets/shared/math/RichMathCache.ets 简单内存缓存：key = hash(text + source + themeVersion)，value = html。 聊天列表消息多时 Web 重建卡顿；缓存无限增长。 最多缓存 80-120 条，超过后删除最旧项；不要持久化缓存。
entry/src/main/ets/shared/components/RichMathRenderer.ets 统一组件：输入纯文本，内部 normalize -> parse -> html -> Web；失败 fallback。 ArkUI Web API 版本、Web 高度自适应、嵌套滚动冲突。 第一版固定/估算高度 + 内部滚动；后续再做 JS bridge 回传高度。
entry/src/main/ets/shared/components/RichMathFallback.ets 不用 Web 时的降级展示，沿用暗色公式块和文本段落。 如果 fallback 又 import 新 renderer，会循环依赖。 Fallback 只 import token 和 ColorTokens，不 import `RichMathRenderer`。
entry/src/main/resources/rawfile/katex/* 本地 KaTeX JS/CSS/font。 当前项目还没有 `rawfile` 目录；资源体积可能变大；路径引用容易错。 先只放最小资源；确认 DevEco 能打包 rawfile；路径统一由 `RichMathHtmlBuilder` 常量管理。

5.2 修改文件

修改文件改什么会和什么冲突处理方式
entry/src/main/ets/overlays/AgentFloatWindow/chat/ChatBubble.ets 把两处 `MathTextRenderer` 换成 `RichMathRenderer`。用户气泡传 `source: 'chatUser'`，AI 气泡传 `source: 'chatAi'`。 你当前还有 AI 浮窗弹出动画改动在 `AgentFloatWindow.ets`，但不直接冲突；真正冲突点是气泡尺寸和 Web 高度。 先限定 `maxHeight`，气泡内部允许滚动；保留 copy/retry/flag 逻辑不动。

六、冲突风险总表

风险为什么会发生影响处理策略
ArkTS 编译冲突 新类型/组件容易写出 `any`、普通 struct 方法、C 风格 for。 DevEco 编译失败。 所有工具函数放 struct 外；struct 内用箭头字段或 @Builder；循环用 `for...of` 或 `while`。
Web 组件 API 版本冲突 项目是 ArkUI 1.1/API 9 风格，部分 Web/Controller API 可能不可用。 Rich renderer 编译或运行失败。 先做最小 Web：加载本地 HTML 字符串或 rawfile；不用高版本 API；失败 fallback。
聊天滚动冲突 Web 渲染完成后高度变化，原 `scrollEdge` 执行太早。 AI 回复后不能自动滚到底。 渲染完成后回调滚动；没有回调时延迟二次滚动。
详情页嵌套滚动冲突 外层 `Scroll` 与公式横向滚动、Web 内部滚动争手势。 长公式或长笔记不好滑。 公式只横向滚动；纵向滚动交给外层详情页；推导组限制最大高度。
AI 输出格式不稳定 模型可能输出 `/frac`、无 delimiter、markdown code fence。 解析错、公式混入正文。 Normalizer 兜底；KnowledgeModel/AgentChatService prompt 只加格式约束。
资源体积/打包冲突 KaTeX font/css/js 加入 rawfile 后包体变大。 构建体积增加，路径配置错误会白屏。 先加最小资源；检查 rawfile 路径；Web 失败时显示 fallback。
当前未提交 AI 浮窗动画 `AgentFloatWindow.ets` 已有本地改动。 如果同时重构浮窗外壳和消息渲染，排查体验问题会混在一起。 先提交或验收动画，再实施 RichMath；RichMath 只改 `ChatBubble/AgentMessageList`。

九、最终判断

这版方案会比旧方案展现更好，前提是坚持“统一富文本渲染层”而不是继续在各页面里补丁式判断公式。它解决的是结构问题：短公式、长公式、推导、正文都有不同展示方式；同时也解决一致性问题：AI 对话和笔记详情看到的是同一套数学排版。

它的代价是实现复杂度更高，需要引入 Web/KaTeX 和缓存。但这是值得的，因为 ArkUI 原生 Text 无法可靠完成真正的 TeX 排版。保底上，fallback 仍能保证内容可读，不会因为渲染失败导致页面空白。

展示更自然公式真排版AI 与笔记一致实现成本更高
